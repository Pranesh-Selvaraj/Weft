# Changelog

All notable changes to Weft are documented in this file. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project intends to follow [Semantic Versioning](https://semver.org/spec/v2.0.0.html) once it publishes releases.

Release notes are written in prose and describe the user-visible effect of each change, not just its label. A published release body must match the entry here.

## [Unreleased]

### Added

- Founding repository: the product definition, the working architecture, and two decision records — the name **Weft**, and the choice of plain-text, git-friendly design files as the canonical artifact that any coding agent can read and write.
- `@weft/core`, the shared document model: a design is a manifest plus one page per file, with nodes in a flat id-addressed map, stable prefixed ULIDs, real text content, token references, captured-page snapshots stored beside the page, and a deterministic JSON writer so identical designs produce identical bytes and reviewable git diffs. The package also ships pure insert, move, reorder, duplicate, remove and update operations, and a dependency-free validator that reports typed, pathed issues for broken references, cycles, unreachable nodes, unresolved tokens and assets, unsafe paths and malformed snapshot metadata.
- A small starter design in `examples/starter.weft/`, readable end to end, exercised by 94 unit tests together with the schema, serialization, validation and operation suites.
- `@weft/design-io`, the Node filesystem layer for design directories. It reads a manifest and the pages it lists, reports schema and file problems together with file-prefixed paths, resolves design-relative paths without allowing escapes, writes manifest and pages atomically with deterministic serialization, formats files into canonical form, initializes new designs without overwriting a non-empty directory unless forced, and checks that referenced asset and snapshot files exist. It also produces the compact summary used by agents.
- The `weft` CLI, the first executable client of the document contract: `weft init`, `weft validate`, `weft fmt` and `weft inspect`, each with human-readable and `--json` output and stable exit codes (`0` success, `1` validation or I/O failure, `2` usage error). `fmt --check` supports CI and pre-commit use, and `validate` distinguishes schema issues from missing files.
- Asset paths are no longer restricted to a fixed list of image/video extensions, so fonts and other design assets can live beside the design without being rejected by the schema.
- The command protocol: serializable page mutations for inserting, updating, moving, removing, duplicating and replacing nodes, plus atomic subtree insertion. Every applied command returns an inverse computed from the document before the change, so a command followed by its inverse restores a byte-identical page. Commands carry a `cm_` id, page id, ISO timestamp and optional human/agent/system actor in an envelope, and untrusted command JSON is parsed with stable error codes before anything is applied.
- Three new CLI commands built on the protocol. `weft apply` reads `{pageId, command, actor?}` from a file or stdin, validates the result, writes atomically, and returns the command id, created node ids, inverse and written files; `--dry-run` returns the same without writing. `weft get` prints a page document or a node with its page context as JSON. `weft id` generates prefixed ULIDs for designs, pages, nodes, assets and commands, so an agent can allocate ids before inserting a node.

- `@weft/contract`, a published structural contract: a JSON Schema draft 2020-12 covering manifests, pages, every node type, paints, styles, layouts, tokens, assets, snapshots, patches, commands, command requests and envelopes, with a versioned `$id` and shared `$defs`. It is hand-maintained and checked against the TypeScript types and validators by a conformance suite.
- A conformance fixture suite that distinguishes structural failures from semantic ones. Valid fixtures must pass both the schema and the core; schema-invalid fixtures must fail both; semantic-invalid fixtures must pass the schema while still failing the core for dangling children, unreachable nodes, multiple parents, unresolved tokens or unsafe paths. The suite also validates the starter design and a page containing every v1 node type, so the schema cannot silently drift.
- `@weft/session`, a Yjs-backed live page session. Node fields are Y.Map registers, parent and fractional order keys live in a separate placement map, and children arrays are derived during materialization, so no `Y.Array` move can duplicate or drop a node. Commands use the same core implementation as the CLI and return their inverse. Two clients that join the same Yjs structure converge after exchanging updates.
- Whole-page file-write ingestion with a three-way merge between the last materialized baseline, the live page and the incoming file. Non-conflicting changes apply; conflicting fields keep the live value and are reported with paths; a file that removes a modified subtree keeps the live subtree and reports a conflict instead of deleting it. The session never writes CRDT metadata into the design file.
- `@weft/render`, a read-only DOM renderer for pages: absolute frame geometry, CSS flex layout, real text, token-resolved colors and font families, solid/gradient/image paints, strokes, radius, shadows, blur, page backgrounds, computed page bounds, asset URL resolution, and sandboxed snapshot iframes when a payload is supplied.
- `apps/web`, the browser editor: a Vite 8 + React 19 app that starts as a static read-only preview loaded through a `virtual:weft-design` plugin and, when served by `weft dev`, becomes a live editor. It shows page tabs, node count, zoom, file changes, conflicts and connection status, and renders frames, flex layout, text, tokens, paints and page bounds as real DOM. `WEFT_DESIGN` points the static preview at another design. Images and snapshots render as placeholders until the asset pipeline supplies them.
- `@weft/bridge` and `weft dev <design.weft>`, the live local loop. The bridge serves the built app, watches the design directory, keeps one Yjs `PageSession` per page, ingests whole-page writes, and streams Yjs updates over `/api/live`. `GET /api/design` bootstraps the manifest and per-page updates. Invalid writes broadcast an error and keep the last good state. The app detects a JSON `/api/design` response, builds sessions, connects to the WebSocket, applies updates, and shows live/connecting/offline status. Editing a design with the CLI updates the open browser without rebuilding.
- Browser editing. Click a layer on the canvas to select it, inspect and edit name, geometry, opacity, fill and text content, delete it, and undo or redo with buttons or Cmd/Ctrl+Z. The selection box follows the DOM layout and live updates. The inspector is intentionally a small property sheet: no drag/resize, layer tree, multi-select, components or page-level commands yet.
- A bidirectional command channel over the live bridge. The app sends `command` messages with a `cm_` command id and an actor; the bridge validates, applies to the Yjs session, writes the changed page atomically with `writePageFile`, marks the session baseline, returns the inverse with `commandResult`, and broadcasts attribution. A failed disk write applies the inverse and rolls the live session back. The bridge is now a canonical writer, not only a watcher.
- Client-side undo/redo stacks backed by command inverses: a successful command pushes its inverse, undo pushes the undo result's inverse onto redo, redo pushes back onto undo. History clears on reconnect, and external CLI/agent file edits remain outside the browser history.
- `writePageFile` in `@weft/design-io`: single-page atomic writes with page validation, used by the bridge and tested independently.
- A light/dark UI theme that defaults to the system preference, switches from the toolbar with a sun/moon control, and persists in `localStorage`. The top bar, canvas, inspector, inputs, buttons, status badges, selection chrome and hints are theme-aware; design content keeps its own colors. The inspector is grouped into Layer, Layout, Appearance and Content sections, with a compact shortcut hint and a cleaner toolbar.
- The workspace picker: `weft workspace dev` starts one live bridge over the registered workspace, and the browser shows a project/design selector in the top bar. Switching designs validates the target against the registry, rebuilds the page sessions, broadcasts a fresh init to every connected tab, and rejects unregistered paths. The editor and inspector continue on the new design without restarting the process.
- The first workspace slice: `@weft/workspace` and `weft workspace init/add/list/remove`. A registry file (`$WEFT_WORKSPACE` or `~/.weft/workspace.json`) holds explicitly registered project roots with canonical real paths, unique names and timestamps. Discovery finds design directories containing `weft.json` inside a registered root while skipping `node_modules`, `.git`, build outputs and symlinked directories. The registry writes atomically with owner-only permissions and reports missing roots instead of silently dropping them. This is the allowlist the future project picker and dev-server supervisor will use; the current bridge still takes one design directory per process.
- Local bridge hardening: loopback-only bind hosts, a random per-run `HttpOnly`/`SameSite=Strict` session cookie, required authorization on `/api/design` and `/api/live`, Host and Origin checks that block DNS rebinding and cross-origin browser requests, constant-time token comparison, a 1 MiB WebSocket payload cap, and restrictive security headers. The browser app receives the cookie automatically; restarting the bridge rotates it and requires open tabs to reload. This is single-user local hardening, not team authentication.
- A repository security baseline: a CI workflow that builds, typechecks, tests, validates and canonicalizes the starter design, and audits dependencies; CodeQL, dependency review, Dependabot, CODEOWNERS and a PR template; `SECURITY.md`, a threat model and a local-workspace design; and scripts for branch protection and repository security settings. `main` now requires pull requests, the `verify`, `analyze` and `dependency-review` checks, with linear history, conversation resolution and no force pushes or deletions.
- The CLI suite is now 21 tests and the workspace registry adds 9; the repository has 190 tests across the document model, design I/O, CLI, contract, session, renderer, bridge, workspace registry, editor command loop and bridge security boundary.
